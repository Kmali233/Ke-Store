# 阶段04：独立后台管理员认证模块详细实现说明

实现日期：2026-10-29。当前实现采用独立Maven模块 `xiaoke-admin`，可打包、启动和配置自己的进程，默认端口8085，context-path为 `/api`。

完成状态：独立模块重写与默认完整验收入口均已通过；375项JUnit、759次HTTP检查，临时进程/数据清理成功，现有业务库未修改。

## 1. 本次重写做了什么

按照用户确认的模块划分，定向撤回上一版散落在user/common中的管理员业务，再在admin中集中实现。没有执行整库Git重置，没有丢弃既有迁移、订单幂等、SKU及其他未提交工作。

| 位置 | 当前职责 |
| --- | --- |
| `xiaoke-admin` | 管理员凭据、账号查询/写入、登录、当前身份、退出、离线初始化和恢复 |
| `xiaoke-user` | 买家注册、登录、个人资料和地址；不提供管理员账号入口 |
| `xiaoke-common` | JWT规则、认证注解/上下文/拦截器、只读账号状态Interface及统一状态校验；没有管理员Controller或账号SQL |
| `xiaoke-product` | 商品业务及本模块只读后台身份Adapter；不维护管理员凭据 |
| `xiaoke-order` | 订单业务及本模块只读后台身份Adapter；不维护管理员凭据 |

根POM新增admin模块。新模块只复用工程已有common、MySQL驱动及 `spring-security-crypto`；没有新增第三方依赖种类或更改版本。认证机制沿用项目MVC拦截器和JJWT，没有引入Spring Security过滤器链。

本阶段没有实现角色权限，也没有把商品、订单业务迁入admin。现有 `@LocalAdminOnly` 商品写入及发货门禁保持原规则，下一阶段再按权限码授权。

### 已撤回的旧放置方式

- user中的 `com.xiaoke.user.admin` 四个业务类迁入admin，user启动器恢复为普通买家服务启动，不再承担离线管理员维护。
- user的application.yml移除后台配置块，user测试结构移除后台表；后台数据库测试迁至admin独立测试库。
- common中的 `AdminIdentityController` 和 `AdminAccountStore` 迁入admin；common不再注册任何管理员业务入口。
- user下的旧《详细实现说明.md》移除，本文为当前说明。根README、SQL说明及验证脚本已调整归属。
- 旧源文件删除不等于旧class自动消失，因此正式验收使用 `clean verify`，还检查最终JAR确实不含旧user/common管理员业务class。

重写前的本地源码快照保存在被Git忽略的 `output/admin-rewrite-backup-20261029-005916/`，只用于本地核对。不要将该快照整体覆盖回工作区，以免覆盖之后的用户改动。

## 2. 接口和身份约定

只有admin进程提供以下接口，默认地址 `http://127.0.0.1:8085/api`：

| 方法/路径 | 认证 | data |
| --- | --- | --- |
| `POST /admin/auth/login` | 公开登录，JSON用户名/口令 | `token`、`expiresIn=1800`、`admin:{id,username}` |
| `GET /admin/auth/me` | 原始后台JWT | `{id,username}` |
| `POST /admin/auth/logout` | 原始后台JWT | null，撤销该账号全部会话 |

完整路径含 `/api`，例如 `POST /api/admin/auth/login`。Controller内部不重复写context-path。其他进程访问这些路径返回404；admin没有买家的 `/api/user/me` 和 `/api/user/login`。

与旧版相比，管理员调用方需要把base URL从user的8083切换至admin的8085；买家仍使用8083。路径与JSON字段保持原样，已有V4账号数据可以继续使用。

继续使用现有请求头契约 `Authorization: <原始JWT>`，不接受Bearer前缀。后台JWT不能进入买家身份入口；买家JWT不能访问admin的me/logout。后台JWT也不替代既有 `X-Local-Admin-Key`。

登录JSON字段只有 `username` 与 `password`。用户名先trim、转小写，限4—50位ASCII字母/数字/下划线。口令保留首尾空格，限12—64位可打印ASCII；初始化/恢复另外要求至少一个字母和数字。ASCII长度限制避免超过BCrypt的72字节边界。字段为write-only，不将口令放进响应对象。

认证路径响应使用 `Cache-Control: no-store`、`Pragma: no-cache`，返回现有 `{code,message,data}` 包装；HTTP状态与code一致。

| 情况 | 结果 |
| --- | --- |
| 用户名不存在、密码错误、禁用/删除账号登录 | 同类401消息，不告知具体账号状态 |
| 未带JWT、签名/用途/issuer/audience/版本/时间不合法 | 401 |
| DTO错误、未知/重复JSON字段、未知查询参数 | 400 |
| admin账号入口在user/product/order上访问 | 404 |
| 身份查询数据库不可用 | 503，不降级为只验证签名 |
| 商品写入/发货缺少现有本地管理条件 | 按既有门禁返回401或403 |

## 3. 数据和令牌设计

继续使用 `sql/migration/V4__admin_auth.sql` 的 `t_admin_account`，与 `t_user` 独立：

| 列/约束 | 作用 |
| --- | --- |
| id | 自增主键；首次初始化固定id=1，防止并发空库初始化创建两个首账号 |
| username及唯一索引 | 独立管理员登录名，ASCII二进制比较，应用规范化小写 |
| password | 60字符BCrypt哈希，不保存明文 |
| status/deleted | 正常与删除状态，数据库CHECK约束限定0/1 |
| token_version | 非负BIGINT撤销版本，初始0 |
| create_time/update_time | 数据库维护的创建/更新时间 |

JWT采用独立Base64密钥，解码至少32字节，不能与已配置的买家密钥相同。admin不启用买家JWT签发，但仍可读取买家密钥来检查误复用。JWT固定HS256、1800秒，含：

```text
iss=xiaoke-admin
aud包含xiaoke-backoffice
purpose=admin
sub=管理员正整数ID
username=规范化用户名
tokenVersion=数据库版本
iat/exp精确相差1800秒
jti=每次签发独立随机标识
```

每次认证都先验证JWT，再通过 `AdminAccountLookup.findById` 读取最新状态，由common的 `AdminAuthentication.requireActive` 统一比较ID、username、version、status和deleted。没有正向身份缓存，因此退出/禁用后的新认证能及时拒绝。

退出由admin本模块执行单条SQL：

```sql
UPDATE t_admin_account SET token_version=token_version+1
WHERE id=? AND token_version=? AND status=1 AND deleted=0;
```

相同旧版本的并发退出只有一次能更新一行，其余返回401。退出撤销全部设备会话；已经通过认证并正在执行的请求不能倒退取消。

V1—V4迁移原文不改。模块重写没有改变表结构，不需要创建V5或重新初始化账号；已有账号哈希、状态和撤销版本继续生效。本次测试不连接现有业务数据库，也不替用户迁移或修改真实账号。

product/order Adapter各有一条仅按ID读取最小状态的SELECT，不读取password，不提供写入方法；账号正常/禁用、版本等规则没有复制到Adapter。当前工程共享MySQL，因此沿用本地SQL读取，没有新增每次请求都远程调用admin的网络依赖。若未来改为数据库自治，应替换这两个Adapter，保持Interface不变。

## 5. 真实调用链

### 登录

```text
POST admin:8085/api/admin/auth/login
→ 外层过滤器清空买家/管理员上下文
→ 公开登录入口和严格输入校验
→ AdminAuthController.login
→ AdminAuthService：查询t_admin_account凭据、BCrypt匹配
→ AdminAuthentication.requireActive
→ admin AdminAccountStore.findById再次读取最新状态
→ 共享规则确认状态和版本
→ AdminJwtService.issue
→ token/expiresIn/admin白名单响应
→ finally清理上下文
```

不存在的用户名也执行dummy BCrypt匹配，减少明显的耗时差异；这不等于限流或严格常量时间认证。

### 查询与退出

```text
GET admin/api/admin/auth/me，Authorization=原始后台JWT
→ @AdminRequired
→ AdminInterceptor
→ AdminAuthentication.authenticate
→ JWT验签和声明校验
→ AdminAccountLookup读取账号，统一检查当前版本/状态
→ AdminContext保存本次身份
→ AdminIdentityController只返回id/username
→ 请求结束清理两类上下文

POST admin/api/admin/auth/logout
→ 相同认证链
→ AdminAuthService.logout
→ admin AdminAccountStore.revoke条件更新version
→ 原JWT再次访问me时，签名合法但版本不一致，返回401
```

### product/order如何一致校验

product/order启用后台认证时注入各自只读Adapter，调用相同的 `AdminAuthentication`。真实数据库测试在这些模块直接验证有效令牌、禁用、删除、版本变更和账号消失；不是只mock Mapper的单元测试。

当前生产JAR没有额外的认证测试Controller，也没有把 `/admin/auth/me` 复制到商品和订单模块。阶段05将实际管理操作标注权限时，再使用已准备的共享认证链。本阶段既有写接口仍由LocalAdminOnly保护。

## 6. 运行、初始化与恢复

全部命令从商城仓库根目录运行。Java工程使用Maven；没有前端包安装或新增npm/yarn依赖。

### 6.1 迁移及构建

按 [SQL说明](../sql/README.md) 设置迁移专用环境变量，核对目标、备份和维护窗口后运行：

```powershell
python scripts/db_migrate.py migrate --maintenance
python scripts/db_migrate.py validate
mvn -B -ntp clean package -DskipTests
```

最后一条只构建并清理旧class，不能当成测试通过。正式验证用第7节命令。

### 6.2 运行配置

admin的application.yml默认 `xiaoke.admin.enabled=true`、端口8085、买家JWT关闭。必须注入 `XIAOKE_ADMIN_JWT_SECRET_BASE64`；缺失、过短、非法或与配置的买家密钥相同会启动失败。可在PowerShell7中生成而不打印：

```powershell
$env:XIAOKE_ADMIN_JWT_SECRET_BASE64 = [Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

dev复用现有 `DB_HOST/DB_PORT/DB_NAME/DB_USERNAME/DB_PASSWORD`；prod显式使用 `DB_URL/DB_USERNAME/DB_PASSWORD`。Spring Boot不会自动读取仓库根.env。密钥和口令不写入仓库，不放在命令行参数中。

product/order的后台认证预留开关是 `XIAOKE_ADMIN_AUTH_ENABLED`，默认false；启用时使用与admin相同的后台密钥，并需要读取共享库的最小账号状态。user已移除该配置。开启预留认证不会替代现有商品/发货门禁。

### 6.3 离线初始化

admin JAR自己负责初始化，不依赖启动user，也不需要生成买家登录令牌。提供数据库配置与后台密钥后，在新的运维终端执行：

```powershell
$env:XIAOKE_ADMIN_PROVISION_ENABLED = 'true'
$env:XIAOKE_ADMIN_PROVISION_MODE = 'create'
$env:XIAOKE_ADMIN_PROVISION_USERNAME = Read-Host '管理员用户名'
$adminPassword = Read-Host '12-64位ASCII口令，至少含字母和数字' -AsSecureString
try {
    $env:XIAOKE_ADMIN_PROVISION_PASSWORD = [System.Net.NetworkCredential]::new('', $adminPassword).Password
    java -jar xiaoke-admin/target/xiaoke-admin-1.0.0.jar --spring.main.web-application-type=none
    if ($LASTEXITCODE -ne 0) { throw '管理员维护失败，请核对脱敏后的错误类型' }
} finally {
    Remove-Item Env:XIAOKE_ADMIN_PROVISION_ENABLED,Env:XIAOKE_ADMIN_PROVISION_MODE,Env:XIAOKE_ADMIN_PROVISION_USERNAME,Env:XIAOKE_ADMIN_PROVISION_PASSWORD -ErrorAction SilentlyContinue
    $adminPassword.Dispose()
}
```

工具要求显式非Web模式，否则在写数据前拒绝；正常启动不自动创建管理员。create只允许空管理员表，重复初始化失败而不改口令。成功后AdminApplication关闭上下文退出。

恢复时将mode改为recover，并输入已有用户名及新口令。恢复更新哈希和版本，撤销旧JWT；不会创建不存在的账号，不会恢复删除状态，也不会自动启用禁用账号。

### 6.4 启动与验证接口

确保provision环境变量已清理，然后运行：

```powershell
java -jar xiaoke-admin/target/xiaoke-admin-1.0.0.jar
```

管理员登录、me、logout均访问8085。买家仍访问user的8083。登录后将token放在原始Authorization头中，退出后再次me应401；在user/product/order访问管理员三个路径应404。

本阶段没有角色管理/禁用HTTP接口。可信的数据库维护操作应把禁用和撤销合成单条更新：`UPDATE t_admin_account SET status=0,token_version=token_version+1 WHERE id=<核对后的ID>`。删除、重新启用或恢复状态时也应递增版本，避免旧令牌重新可用。下一阶段再封装授权入口。

## 8. 失败恢复、事实边界与后续

- 模块迁移只改变代码归属，不回滚数据库；保留V4和已有管理员数据。代码回退不能恢复旧密码或撤销版本。
- 使用旧备份恢复数据库可能复活旧版本会话；恢复流程需同时考虑签名密钥轮换，不可直接假定旧JWT无效。
- 退出响应丢失时版本可能已提交，原令牌401后重新登录即可；没有自动重试写事务。
- 认证组件对数据库故障返回503，不忽略状态/版本检查。连接池恢复需要时间，验收器等待真实SQL就绪后再进行业务写入。
- 已通过认证进入业务的请求不能被后续退出撤回；阶段05的管理写操作需要结合权限和事务设计。
- 当前共享HMAC密钥的验证进程也具备签名能力；非对称密钥、轮换窗口、MFA、登录限流、按设备退出、refresh token、完整审计表与云部署不属于本阶段。
- 没有管理员前端页面；浏览器凭据存储、HTTPS和部署环境联调未执行。本地并发测试不代表生产容量或安全认证。
