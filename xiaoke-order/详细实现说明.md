# 阶段02：下单请求幂等功能——详细实现说明

实现日期：2026-10-27。代码仓库：`D:\qwq\Desktop\项目大全\小Ke商城\小Ke商城`。本说明对应阶段02，只讨论下单请求幂等与其必要的迁移、接口和验证改动。

## 1. 完成了什么，解决什么问题

原来的 `POST /api/order` 每收到一次请求就尝试创建一笔新订单。用户重复点击，或者服务端已提交而客户端没有收到响应，再发一次相同请求可能创建第二笔订单、再扣一次库存。

本次增加 `Idempotency-Key` 请求头。用户首次提交前生成一个随机键，同一笔业务意图的重发保留原键、原内容。服务端用“当前登录用户ID＋键”定位成功回执：同内容返回首次订单，不重新扣库存；不同内容返回409。不同用户可以使用相同的键。

例如库存10，买家使用键 `checkout-001` 购买2件，首次创建订单A，库存变8、sales变2；同时向两个order进程重复提交相同请求，最终仍只有订单A和一份成功回执。之后订单A被取消，重放仍返回A的首次创建结果，不生成订单B。真的要再买一次必须使用新键。

### 能力来源与边界

| 类型 | 内容 |
|---|---|
| 原来已有 | JWT和账号状态校验、严格DTO校验、商品HTTP预读、数据库价格和收货快照、用户/分类/商品锁、订单库存本地事务、单号唯一索引与有限重试、支付/发货/取消 |
| 本次新增 | 幂等头契约、v1规范化摘要、成功回执表、事务内二次检查和原子保存、按键查询结果、真实幂等并发与故障验收、V2测试结构回放 |
| 现有第三方能力 | MySQL InnoDB事务/行锁/联合主键；Spring TransactionTemplate；MyBatis映射；Jackson序列化；阶段01已有Flyway迁移工具 |
| 没有扩展 | 新前端下单页面、SKU、真实支付、Redis/MQ、分布式事务、高吞吐订单号算法；没有增加生产依赖 |

当前兼容旧客户端：不带键仍按原语义创建订单，不能把无键调用描述为已获得幂等保证。本次没有迁移真实业务数据库，实际验收使用独立临时实例。

## 2. 接口契约

### 2.1 创建订单

```http
POST /api/order
Authorization: <当前买家的原始JWT>
Idempotency-Key: checkout-001
Content-Type: application/json
```

```json
{
  "items": [{"productId": 1, "quantity": 2}],
  "receiverName": "测试收货人",
  "receiverPhone": "000",
  "receiverAddress": "测试地址",
  "remark": "工作日送达"
}
```

以下是响应结构示意，订单号和金额由实际数据决定：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {"orderNo": "20261027000001", "status": 0, "totalAmount": 24.68}
}
```

| 请求情况 | 结果 |
|---|---|
| 同用户、同键、同规范化内容 | 200，返回首次orderNo/status/totalAmount |
| 同用户、同键、不同规范化内容 | 409，不新增订单和扣库存 |
| 不同用户、相同键 | 各自独立，不泄露其他用户结果 |
| 未传键 | 保留原行为，可产生多笔订单 |
| 传空键/非法字符/超过64字符/重复头 | 400；不会自动降级为无键 |
| 账号不存在/删除，或账号禁用 | 仍返回401或403，回执不会绕过账号检查 |

键规则是 `[A-Za-z0-9_-]{1,64}`，区分大小写、不trim。新客户端应使用UUID等足够随机的键，并在发请求前保存好。每次重试都生成新键会绕开幂等作用域。

### 2.2 查询创建结果

```http
GET /api/order/idempotency/checkout-001
Authorization: <当前买家的原始JWT>
```

200返回原始创建结果；404表示此时没有看到本人对应键的已提交成功记录。**404不等于确认回滚**：请求可能仍在执行，也可能在查询之后才提交。保留原键稍后再查，需要重发时也只使用原键和原内容。数据库故障时查询可能503。

回执里的status是首次创建状态0；后续当前状态使用 `GET /api/order/{orderNo}/status`。已取消或软删订单的回执仍能返回原结果，不能拿它当作当前可支付状态。

## 3. 摘要如何判断“同一内容”

`OrderCreateDTO`原有setter先trim手填收货字段和备注；空白备注转null。原有验证仍要求商品1–20项、商品ID不能重复、数量合法、引用地址与手填收货严格二选一。

`OrderIdempotency.request`把请求转为固定位置数组，用Jackson生成UTF-8 JSON字节，再用JDK自带SHA-256计算64位十六进制摘要。不是直接对原始HTTP JSON做哈希。

v1数组定义：

```text
[
  1,
  按productId升序排列的 [[productId, quantity], ...],
  ["address", addressId] 或 ["manual", name, phone, address],
  remark或null
]
```

因此JSON字段顺序、商品列表排列和DTO已经归一化的首尾空白不影响摘要；商品ID、数量、收货来源、地址ID、手填收货字段、备注的实际变化会影响摘要。固定JSON数组避免直接用 `|` 拼接字符串带来的歧义。

商品价格、当前库存、商品状态、引用地址的当前内容不参与摘要。它们是首次成功时由服务端确定的快照；如果每次重放都读取这些当前值再计算摘要，商品调价或地址修改会错误地把原请求变成新请求。

摘要格式带版本号，数据库也保存 `hash_version=1`。单元测试固定了一组v1字节对应的摘要，避免重构时悄悄改变契约。以后接入SKU或调整规范化必须保留旧版本的解释能力；当前未知版本回执返回409并阻止复用，不自动删掉回执重新下单。

## 4. 数据库改动与生命周期

新增文件：`sql/migration/V2__order_idempotency.sql`，不修改已交付V1和其结构快照。

| 字段/约束 | 作用 |
|---|---|
| user_id + idempotency_key 联合主键 | 每个用户的每个键至多一份成功回执；ascii_bin确保键区分大小写 |
| hash_version / request_hash | 记录规范化版本和请求意图摘要 |
| order_no，唯一索引 | 每份创建回执对应唯一订单号 |
| result_status / total_amount | 保存首次创建时的原始业务结果 |
| create_time | 回执创建时间，不作为TTL |

回执不额外保存收货姓名、电话、地址正文，也不保存JWT。它没有单独的“处理中/失败”持久状态：只有整笔事务提交后才有可见成功回执；失败随订单和库存一起回滚。

成功键**永久保留，无TTL、无自动清理、无到期复用语义**。订单取消、软删、归档都不应该删回执。未来确需清理时应另行设计不可复用墓碑、历史摘要兼容和结果查询策略。本阶段不做无限量数据增长治理，不能擅自通过定期删表记录解决容量问题。

## 6. 从HTTP到数据库的真实调用链

### 首次带键下单

```text
POST /api/order
  → common登录拦截器校验JWT及账号
  → OrderController：解析单个Idempotency-Key和合法DTO
  → OrderCommandFacade.create(uid,dto,key)
      → OrderInput.check / OrderUsers.check
      → OrderIdempotency.request：生成v1摘要
      → replay(...,false)：普通查询已提交回执
      → 未命中：ProductDetailHttpClient.preread（事务与JVM锁之外）
      → 按日JVM锁（原单号策略）
      → OrderTransactionService.createOnce
          → OrderTransactions.create：新事务、READ_COMMITTED
          → users.lock：SELECT用户 FOR UPDATE
          → replay(...,true)：锁定读取本人键，二次检查
          → 未命中：读本人地址快照，锁分类和商品，校验价格/库存
          → 分配单号，扣库存/增加sales，插订单和全部明细
          → OrderIdempotency.save：插入成功回执
          → 提交以上全部SQL
      → 事务完成后释放按日锁
  → Result.success(原始OrderCreateVO)
```

### 成功重放

```text
同用户、同键、同内容
  → 身份和DTO校验
  → 规范化摘要
  → 查回执并比对版本/摘要
  → 直接恢复OrderCreateVO并返回
```

快速重放不读当前商品/地址，不调用商品HTTP，不重新分配单号或扣库存。若商品HTTP预读期间另一个进程刚刚提交，预读失败分支还会再查一次成功回执，有已提交结果则返回；没有结果就保留原故障，不把查询未命中当作业务成功。

### 按键查询

```text
GET /api/order/idempotency/{key}
  → 登录和账号检查
  → OrderCommandFacade.creationResult
  → OrderIdempotency.lookup
  → Mapper.find(uid,key)
  → 返回原始回执，或404/基础设施错误
```

## 7. 为什么两个进程不会各建一单

仅靠单进程内存缓存或JVM锁，order_a与order_b无法互相排斥。本次沿用数据库用户行锁作为串行化点：两个请求都先在创建事务中锁相同用户行，后到者等待前一个事务提交或回滚，再读取回执。

先到者提交：后到者看到回执，同摘要返回原结果，异摘要409。先到者回滚：没有成功回执、库存和订单也恢复，后到者才有机会执行首次创建。

数据库联合主键还提供最后的唯一约束。锁序为“用户→幂等回执→地址→分类升序→商品升序”，在碰商品之前就判断重放。当前这一串行化会让同一用户的不同键也排队，是复用原用户锁的简单取舍；尚未做同用户吞吐优化。

已有订单号分配仍使用按日JVM锁＋MAX＋唯一索引，只有已确认的订单号唯一键碰撞才有限重试；幂等不等于高吞吐多机编号系统。

## 8. 失败场景与恢复

| 场景 | 数据库结果与调用方做法 |
|---|---|
| 首次HTTP预读失败 | 没开始写事务；若并发已产生成功回执可返回它，否则报原故障，保留原键 |
| 库存不足/商品不可售 | 不保存成功回执；已开始的SQL整笔回滚 |
| 插入订单/明细/回执失败 | 全部写入及库存一起回滚；排障后原键原内容重试 |
| 已提交但HTTP响应丢失 | 客户端先按键查，或在确认恢复流程后原键原内容重发；返回原订单 |
| 提交确认未知 | 不在服务端盲目重做；先按键查，数据库不可用则等待恢复，不能换新键 |
| 同键修改数量/收货/备注 | 409；若是另一笔购买则生成新键 |
| 商品服务停止/商品已下架 | 已成功键仍可返回回执；首次新键仍按既有依赖要求失败 |
| order进程重启 | 回执在MySQL，重新启动后仍能找到原结果 |

验收分别采用真实回执写入故障、真实代理丢弃HTTP响应、真实order进程停止重启；“提交确认丢失”还在JUnit中使用真实提交后抛事务完成异常模拟。后者证明应用处理分支，没有模拟网络层数据库COMMIT应答包的丢失。

## 13. 已知限制与后续衔接

- 幂等以客户端稳定复用键为前提；无键兼容没有截止日期，本阶段也没有新前端强制键接入，需要后续买家端阶段完成。
- 成功回执永久增长，当前没有归档、容量压测或保留期治理；未来不得通过删记录让旧键重新变成新单。
- 依赖多个order进程共享同一MySQL写库；没有跨数据库、跨地域容灾保证。普通读取与锁定写都使用当前同一数据源，不能随意把快速回执查询换成可能延迟的只读副本。
- 同用户串行化、按日JVM锁与既有编号有限重试限制吞吐；本阶段验证正确性，未做生产容量或时延SLO验收。
- 不保证任意人工删库、物理删除回执后仍能去重；数据备份、恢复和历史结果必须一起保护。
- 后续SKU阶段要保留v1语义；支付回调/退款幂等属于各自业务状态机，不能直接套用下单键替代。
- 未对真实业务库执行迁移，未进行云端或生产环境发布，未接真实支付渠道。不能把隔离环境验收表述为这些外部环境已验证。
