# 小Ke商城（xiaoke-mall）

阶段04后台认证采用独立 `xiaoke-admin` Maven模块，默认端口8085（保留原AI端口8084），统一拥有 `/api/admin/auth/login`、`/me`、`/logout` 及离线账号初始化/恢复。user只承载买家业务；common仅保留共享认证规则与只读查询契约；product/order通过各自适配器读取共享MySQL中的最小账号状态。先迁移V4，再为admin注入独立后台密钥。配置、调用链、迁移兼容和本轮验收结果见[后台管理员认证详细实现说明](xiaoke-admin/详细实现说明.md)，完整验收入口为 `python scripts/verify-admin-auth.py`。现有商品写接口和订单发货仍使用本地管理门禁，阶段05再实现角色授权。

阶段03已增加SPU/SKU规格：商品详情返回独立SKU价格/库存；新订单使用skuId并保存规格快照；旧productId请求映射默认SKU，历史订单和v1幂等键继续兼容。部署前停止旧product/order写进程，通过迁移入口完成V3及默认SKU回填。接口与边界见[商品规格详细实现说明](xiaoke-product/详细实现说明.md)，完整验收入口为 `python scripts/verify-skus.py`。本地规格选择页为product服务的 `/api/sku-demo.html`。

> **一个对标小米商城的简化版自营电商平台。** 先把一套真实、可控、能讲透的业务体系搭起来，再在它之上做一个既能答政策、又能查真实订单的 AI 客服；后续按月度版本持续迭代。

本项目不是一个「什么都做一点」的课堂练习，而是一次**有边界、有取舍、可演进**的工程实践。

## 一、为什么是「简化版小米商城」

### 1.1 选场景的三条硬标准

因此本项目的场景筛选标准是三条：

| 标准 | 要求 | 为什么 |
|---|---|---|
| **体量可控** | SKU 数量在千级以内 | 意图树能覆盖全、评估集能写完整、检索难点能说清楚 |
| **品类多元但不泛滥** | 覆盖 6 个左右一级品类 | 有跨品类对比的复杂度，又不会膨胀到无法建模 |
| **是独立业务体系** | 自营 + 独立平台 | 有完整的商品文档、售后政策、FAQ 可调研，不用编造 |

**核心原则：小比大强，真比编强。** 300 个 SKU 能讲透，远胜过几百亿个 SKU 只能浅显带过。

### 1.2 为什么对标「小米商城」

在候选品牌里（华为商城、Apple Store、小米有品、网易严选、京东京造、MUJI、戴森……），小米商城是与本项目目标最匹配的一个：

| 维度 | 小米商城 | 适配度 |
|---|---|---|
| 模式 | 自营 + 独立 APP | ✅ 业务闭环清晰，无第三方商家带来的复杂度爆炸 |
| 品类 | 手机 / 电视影音 / 笔记本平板 / 智能家居 / 出行穿戴 / 生活周边 | ✅ 6 大品类，跨品类对比场景天然存在 |
| SKU 量级 | 数百级（本项目取 **约 300 个**） | ✅ 落在「可控」区间，意图树可覆盖完整 |
| 生态特征 | 硬件 + 生态链，配件兼容性与 IoT 联动强 | ✅ 天然产生「配件能否兼容」「设备怎么联动」这类高价值问答 |

**参考而不是照抄。** 项目里的品类划分、商品参数结构、售后政策口径，都以小米商城官网/APP 的真实组织方式为调研来源，但在体量上做了裁剪——保留复杂度，去掉个人项目驾驭不了的规模。

### 1.3 场景边界：明确做什么、不做什么

写明「不做」和写明「做」同样重要。**v1.0 只做支撑 AI 客服闭环的那条线**：

| 范围 | v1.0 | 说明 |
|---|---|---|
| 用户（注册 / 登录 / 身份） | ✅ 做 | 没有身份就查不了「我的订单」 |
| 商品（目录 / 详情 / 搜索） | ✅ 做 | AI 客服的知识与数据来源 |
| 订单（查单 / 物流状态） | ✅ 做 | 工具回查的落点 |
| AI 客服（知识问答 + 工具回查） | ✅ 做 | 本项目的核心目标 |
| 前端静态商城页 + 悬浮助手 | ✅ 做 | 让闭环可演示 |
| 购物车 | ❌ 不做 | AI 客服场景不依赖，列入 v1.1 |
| 支付与退款资金流 | ❌ 不做 | 涉及第三方对接，与主题无关，列入 v1.2 |
| 优惠券、营销、评价、库存并发 | ❌ 不做 | 与客服场景无关 |
| 人工坐席工作台 | ❌ 不做 | 只做「转人工」出口 |

## 二、场景拆解（本项目的重点）

场景不是编出来的，是**调研出来再拆解出来的**。下面是从「一个真实品牌」到「可执行工程」的四步。

### 2.1 第一步：确定业务体量

| 项 | 设定 | 依据 |
|---|---|---|
| SKU 总量 | 约 300 | 落在 200–500 的理想区间，可全量建模 |
| 一级品类 | 6 | 手机 / 电视影音 / 笔记本平板 / 智能家居 / 出行穿戴 / 生活周边 |
| 商品属性 | 参数表 + 对比维度 | 支撑「A 和 B 有什么区别」这类跨商品比对 |
| 用户角色 | 游客 / 已登录买家 / 知识库管理员 / 人工客服 | 决定「能查什么、不能查什么」 |

### 2.2 第二步：梳理意图体系

把用户会问的问题，按 **3 个一级意图 + 22 个二级意图** 分层组织。每个二级意图都有真实用户问法示例，且明确它的**处理通道**（知识检索 / 工具回查 / 拒绝或转人工）：

| 一级意图 | 二级意图（示例） | 处理通道 |
|---|---|---|
| **售前咨询** | 商品参数查询、跨品类商品对比、选购建议、库存与到货、价格与优惠、发票政策、配送范围与时效、保修政策、以旧换新、配件兼容性 | 知识检索 + 商品服务查询 |
| **售后咨询** | 订单状态查询、物流轨迹查询、退换货政策、退款进度、质量问题处理、维修与上门服务、订单取消与修改、售后时效 | **工具回查订单服务** + 知识检索 |
| **边界与兜底** | 转人工、越界拒答、多轮指代消解、敏感信息保护 | 流程控制 |

> **这一节是场景设计里最有价值的部分**：它直接决定了系统「光有知识库够不够」。售后咨询里有整整一类问题（订单到哪了、什么时候发货）需要**实时交易数据**，向量库既滞后又无法做用户级隔离 —— 正是这个观察催生了本项目的「双通道」架构（见第三节）。

### 2.3 第三步：构建知识文档体系

参考小米商城真实的文档组织方式，构建分层知识库。**刻意埋入结构化内容**（参数表、对比表、故障树），模拟真实场景的检索难点：

| 文档类型 | 内容 | 埋的检索难点 |
|---|---|---|
| 商品文档 | 每品类/系列的商品详情、参数、卖点 | 参数表、跨型号对比表 |
| 售后政策 | 退换货、保修、维修、发票规则 | 条件分支多，需精确匹配 |
| 常见问题 FAQ | 按一级意图分级组织 | 同义问法多，需语义召回 |
| 物流与配送 | 配送范围、时效、运费规则 | 地域/品类条件组合 |
| 售后诊断 | 典型故障的排查步骤 | 决策树式 step-by-step |

### 2.4 第四步：设计评估集

**效果不能靠「我觉得不错」。** 基于意图体系设计 60–100 条评估样本，按类型配比，标注难度与预期答案：

| 类型 | 占比 | 用途 |
|---|---|---|
| 政策类问题 | 主体 | 测知识检索准确性 |
| 商品类问题 | 主体 | 测参数比对与跨品类检索 |
| 订单类问题 | 20% | 测工具回查链路 |
| **知识库未覆盖** | 15% | 专测模型会不会编造（幻觉） |
| 越界问题 | 10% | 测拒答边界 |
| 对抗类（提示词注入等） | 5% | 测安全 |

评分采用**正确性 / 引用准确率 / 表达质量 / 安全合规**四维打分（每条 0–2 分），并记录模型版本、提示词版本、检索参数，保证调整前后**可对比、可回归**。

## 三、系统架构

场景拆解的结果，是三层**完全解耦**的结构——不共享任何代码，只通过 HTTP 交互：

```
┌───────────────────────────────────────────────┐
│  前端：静态商城页 + 悬浮 AI 客服组件（消费 SSE）  │
└──────────────────────┬────────────────────────┘
                       │ HTTP / SSE
┌──────────────────────▼────────────────────────┐
│  商城业务服务（Spring Boot 多模块）              │
│  xiaoke-user   ·  xiaoke-product  ·  xiaoke-order│
│  xiaoke-ai（BFF）：代理 RAG + 工具回查 + 降级     │
└──────────┬─────────────────────┬──────────────┘
           │ HTTP                │ 工具调用（同进程内）
           │                     └─ 订单服务 / 商品服务
┌──────────▼────────────────────────────────────┐
│  独立的 RAG 知识库服务（Ragent）                 │
│  文档检索 · 向量召回 · 重排 · 多轮对话            │
│  PostgreSQL + pgvector                          │
└───────────────────────────────────────────────┘
```

### 两个关键判断

1. **光有知识库做不成客服。** RAG 只能回答静态知识，而客服最高频的问题之一是「我的订单到哪了」——这是实时交易数据。因此设计了**双通道**：静态知识走向量检索，实时数据走**工具回查**（模型识别到订单类意图 → 调用订单服务接口 → 拿到结构化数据后自己组织语言）。
2. **权限边界严格约束。** 工具只暴露「订单号」这类无法越权的参数；**用户身份必须由服务端从会话中取**，绝不信任模型传入的用户 ID；查询结果服务端二次校验归属；「查不到」与「无权限」统一返回 404，避免用错误码探测订单是否存在。

### 可用性设计

任一服务重启或不可用，都不影响另外两个独立运行。AI 客服侧做**熔断降级**（Ragent 不可达 → 返回「客服暂时不可用」，不暴露内部错误；工具不可达 → 引导转人工）；流式请求**不做自动重试**，避免用户看到重复内容。

## 六、快速开始

1. 数据库统一使用 [增量迁移入口](sql/README.md)：空库显式 migrate；已有库先停写、核对结构、备份后显式 baseline。`sql/xiaoke_mall.sql` 只保留为历史参考，其中的 DROP TABLE 不再用于正常初始化或升级。
2. 在 IDEA Run Configuration 的环境变量或启动进程环境中显式设置 `DB_USERNAME`、`DB_PASSWORD`；dev 可选 `DB_HOST`、`DB_PORT`、`DB_NAME`，prod 提供完整 `DB_URL`。均不提供默认账号口令，根目录 `.env` 不会被自动加载。
3. 启动商品服务：运行 `ProductApplication`，端口 `8081`，统一前缀 `/api`
4. 示例接口（商品）：

   | 操作 | 接口 |
   |---|---|
   | 分页 | `GET /api/product/page?pageNum=1&pageSize=10` |
   | 详情 | `GET /api/product/{id}` |
   | 新增 | `POST /api/product` |
   | 修改 | `PUT /api/product` |
   | 删除 | `DELETE /api/product/{id}` |
   | 搜索 | `GET /api/product/search?keyword=手机` |
   | 参数读取 / 覆盖 | `GET /api/product/{id}/attrs`、`POST /api/product/{id}/attrs` |
   | 分类列表 / 新增 | `GET /api/category/list`、`POST /api/category` |
   | 分类修改 / 删除 | `PUT /api/category`、`DELETE /api/category/{id}` |

商品模块当前契约与阅读顺序见 [xiaoke-product/README.md](xiaoke-product/README.md)。公开查询只展示上架且分类祖先均可见的商品。商品资料 PUT 中的库存只用于核对，不能覆盖库存；对外 `orderCount` 映射既有 `sales` 列，表示已创建且未取消的下单件数。

**用户服务（2026-10-22 已实现）**

配置上述数据库环境变量，并提供 `XIAOKE_JWT_SECRET_BASE64`（密码学随机的至少 32 字节经 Base64 编码）。运行 `UserApplication`，或从根目录执行 `mvn -B -ntp -pl xiaoke-user -am package` 后执行 `java -jar xiaoke-user/target/xiaoke-user-1.0.0.jar`。

| 操作 | 接口 |
|---|---|
| 注册 / 登录 | `POST /api/user/register`、`POST /api/user/login` |
| 当前用户 | `GET /api/user/me` |
| 地址新增 / 列表 | `POST /api/address`、`GET /api/address/list` |
| 地址修改 / 删除 | `PUT /api/address`、`DELETE /api/address/{id}` |
| 默认地址 | `PUT /api/address/{id}/default` |

注册和登录公开；其余接口使用 `Authorization: <原始JWT>`，没有 Bearer 前缀。第一条地址省略 isDefault 时自动默认，显式 false 会被尊重，删除默认地址不自动转移。生产环境显式激活 prod 并提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 和 JWT 密钥。

从 [UserController.register](xiaoke-user/src/main/java/com/xiaoke/user/controller/UserController.java) 开始阅读，再追踪 DTO → UserServiceImpl → 密码配置 → 注册事务组件 → Mapper。用户写事务最终统一使用 UserTransactions/TransactionTemplate，在确认回滚后转换锁冲突；不要给外层业务再套事务。

测试从根目录运行 `mvn -B -ntp package`。真实 MySQL 集成测试仅在 `XIAOKE_USER_DB_TESTS=true` 且提供 `XIAOKE_USER_TEST_DB_URL` 时启用，测试库名必须匹配 `xiaoke_user_verify_*`；测试会清空其用户和地址数据，使用专用隔离实例。默认跳过该组，不代表数据库测试已经通过。

**订单服务（2026-10-24）**

订单服务使用与user相同的数据库和 `XIAOKE_JWT_SECRET_BASE64`，启动 `OrderApplication` 或构建后运行 `java -jar xiaoke-order/target/xiaoke-order-1.0.0.jar`，端口8082。创建订单前启动product，`PRODUCT_BASE_URL` 在dev默认 `http://127.0.0.1:8081/api`，prod必须显式配置。

订单接口为 `POST /api/order`、`GET /api/order/idempotency/{key}`、`GET /api/order/page`、`GET /api/order/{orderNo}`、`GET /api/order/{orderNo}/status`、`POST /api/order/{orderNo}/pay`、`POST /api/order/{orderNo}/ship`、`POST /api/order/{orderNo}/cancel`。七个买家接口使用原始JWT；ship使用本地管理门禁。完整契约、收货二选一、库存事务和阅读顺序见 [xiaoke-order/README.md](xiaoke-order/README.md)。

订单快照、库存扣减/恢复和下单件数使用同库事务；order通过自有适配Mapper访问关联表，不依赖user/product业务jar。阶段02支持 `Idempotency-Key`：同用户同键同内容返回首次创建结果，同键异参409；旧客户端不带键仍可能创建多单。需先应用V2迁移，键永久保留。模拟支付/取消不涉及真实资金。实现与验收见 [详细实现说明](xiaoke-order/详细实现说明.md)。

真实订单数据库测试需要 `XIAOKE_ORDER_DB_TESTS=true` 和 `XIAOKE_ORDER_TEST_DB_URL`，仅允许专用 `xiaoke_order_verify_*` 库。测试会清空该库并注入故障，默认跳过。阶段02完整复现入口为 `python scripts/verify-idempotency.py`，包括隔离数据库、迁移、全部JUnit和双订单进程HTTP并发与故障验证。

**多服务启动**

2026-10-23：商品模块五个 GET 公开，七个管理写接口默认返回403。仅本机开发需要写操作时，显式设置 `SPRING_PROFILES_ACTIVE=dev`、`LOCAL_ADMIN_KEY` 并开启 `xiaoke.local-admin-enabled=true`（环境变量 `XIAOKE_LOCAL_ADMIN_ENABLED=true`），请求携带 `X-Local-Admin-Key`。门禁还要求未激活 prod、监听与直接来源均为 IPv4 `127.0.0.1`。未来新增管理接口同样必须标注 `@LocalAdminOnly`。

- **IDEA**：Reload 父工程后，每个服务的 `*Application` 各生成一条运行配置，可分别或同时启动。
- **命令行**：单服务启动 `mvn -pl xiaoke-product spring-boot:run`；全部构建 `mvn clean install`；jar 启动 `java -jar xiaoke-product/target/xiaoke-product-1.0.0.jar`。

**新增后续服务**

只复用已有服务的POM、配置和启动骨架，为新服务建立自己的包、Mapper和业务代码，并加入父POM聚合。order已经建立，不需要再次复制商品服务。

## 七、迭代路线

**推进策略：纵向切片，不横向铺开。** 判断一个功能现在做不做的唯一标准是「AI 客服会不会用到它」。

| 里程碑 | 目标 | 状态 |
|---|---|---|
| **M0** 规范与环境 | 文档集、端口规划、密钥外置、中间件编排 | 进行中 |
| **M1** 用户服务 | 注册、登录、身份与地址八接口 | 已实现并验证 |
| **商品目录** | 商品、分类、参数十二接口 | 已实现；验收见商品模块说明 |
| **M2** 订单服务 | 订单七接口、快照、同库库存和下单件数联动 | 已实现；验收见订单模块说明 |
| **M3** AI 客服链路打通 | 跑通「提问 → 查真实订单 → 流式回答」闭环 | 待开始 |
| **M4** 前端助手与评测 | 悬浮组件 + 60–100 条评测集 + 基线报告 | 待开始 |

## 八、工程约定

最终系统验收可在仓库根目录运行 `python scripts/verify-system.py`。脚本创建独立MySQL实例，执行全量 `clean verify`、两个order进程的真实HTTP并发、库存账本核对和服务中断503检查，最后清理临时环境。依赖、参数与证据位置见 [scripts/README.md](scripts/README.md)。

1. **ADR 只增不改**：架构决策一旦记录，后续若推翻，新增一条说明「取代 ADR-00X」，不修改原文——保留决策痕迹。
2. **接口先改文档再改代码**：契约文档是前后端的唯一事实来源。
3. **指标必须有口径**：凡出现「快」「准」这类词，必须给出可测量的定义与测量方法。
4. **返回值统一**：各服务用 `Result` 包装返回值，业务错误抛 `BusinessException`。
5. **金额禁止 FLOAT/DOUBLE**，统一 `DECIMAL(10,2)`；状态字段必须用枚举类，禁止魔法数字。
6. **无明文密钥进仓库**：API Key、数据源口令全部环境变量注入。
