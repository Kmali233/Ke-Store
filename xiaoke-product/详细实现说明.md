# 阶段03：SPU与SKU商品规格模块——详细实现说明

实现与验收日期：2026-10-28。业务仓库：`D:\qwq\Desktop\项目大全\小Ke商城\小Ke商城`。本阶段同时改商品与订单模块，保持多个进程共享MySQL、本地事务维护库存的现有架构。

## 1. 本阶段实现了什么

现有商品 `t_product` 作为SPU，表示一类商品，例如“测试手机”；新增 `t_product_sku` 表示可购买规格，例如“黑色＋256GB”和“白色＋512GB”。每个SKU有独立价格、库存、未取消下单件数、图片和上下架状态。

下单明细支持skuId，服务器锁定SKU后取价格、扣库存，并保存商品名、SKU名、规格、图片、单价快照。同一SPU可以在一单中购买多个不同SKU。取消只恢复原SKU，不能串到兄弟规格；下架或软删SKU不影响已发生订单的取消恢复。

### 一个真实验收例子

验收脚本创建一个SPU和两个规格：黑色256GB单价20.50、库存4；白色512GB单价30.00、库存6。黑色买2件、白色买1件，总额71.00，库存分别变为2和5，默认SKU保持不变。后台改名、改价和改规格后，订单快照仍保持原值；黑色SKU软删后不能新买，但取消原订单仍恢复黑色4件、白色6件。

## 2. 数据模型与唯一库存权威

### 2.1 新表和订单字段

`sql/migration/V3__product_sku.sql`新增两张表：

| 表/字段 | 实际用途 |
|---|---|
| t_product_sku.id / product_id | SKU身份和所属SPU，归属不通过更新DTO修改 |
| name / spec_json / spec_hash | SKU显示名、规范化规格JSON、规格组合SHA-256 |
| price / stock / sales | SKU唯一交易价格、库存、已创建且未取消的下单件数 |
| image / status / deleted | 可选SKU图片、上下架、软删；删除不清空库存和sales |
| is_default / default_product_id | 默认SKU标识；生成列将默认行映射为product_id，其余为NULL，唯一索引约束每SPU至多一个默认SKU |
| uk_sku_specs(product_id,spec_hash) | 同SPU的规格组合唯一；软删行仍保留约束 |
| t_catalog_migration.version / completed_at | 默认SKU回填完成标记，version=3代表本次切换回填与核对已结束 |

`t_order_item`增量增加可空字段 `sku_id`、`sku_name`、`sku_spec` 和SKU索引。新订单全部写入这三个快照字段；历史记录保持NULL，不拿今天的SKU名称/规格去改写过去的订单。

### 2.2 谁负责写什么

| 数据 | 商品进程 | 订单进程 |
|---|---|---|
| SPU名称、分类、描述、图片、可见状态 | 按原分类锁序管理 | 只读/锁定，用于校验与快照 |
| SKU名称、规格、单价、图片、状态、软删 | 本地管理接口维护 | 锁后读取，不能相信客户端单价 |
| SKU初始stock | 创建SKU时赋初值 | 不负责初始化 |
| SKU stock/sales的交易变化 | 资料更新禁止覆盖；stock只核对 | 下单stock-q/sales+q，取消stock+q/sales-q；与订单共用本地事务 |
| SPU原price/stock/sales | 创建新SPU时记录初始来源；旧值保留用于迁移核验 | 不读作交易权威，不再扣减/恢复这些列 |
| 订单和明细/幂等回执 | 不写 | 原有归属，新增SKU快照与同事务回执 |

保留SPU旧列是兼容结构和保留迁移来源，不是维护两套实时库存。应用接口没有第二个库存覆盖入口；本阶段没有实施数据库列级授权隔离，因此必须停止旧二进制和其他旧写入者，不能让它们继续写SPU列。

### 2.3 商品列表与详情的展示口径

- price：上架、未删SKU最低单价，包括库存为0的上架SKU。
- stock：上述上架、未删SKU的库存之和。
- orderCount：全部SKU的sales之和，包含下架、软删SKU，避免把未取消订单的计数隐藏。
- 聚合stock/orderCount用Long，单SKU库存仍是非负Integer。
- 没有上架SKU时price/stock为0，详情skus数组为空；不能把聚合price=0解释为有货或免费可买。SKU单价本身允许合法0元，最终可购买性由SKU状态/库存决定。
- SKU图片为空时，下单快照回退为SPU图片。商品详情仍保留原attrs，描述参数与可购买规格是不同概念。

## 3. 接口契约与规格规范化

### 3.1 SKU管理

以下路径含`/api`，三个管理写接口均沿用`@LocalAdminOnly`：显式dev、本机IPv4、管理开关及正确密钥齐全才可调用；普通买家JWT不授予管理权限。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | /api/product/{pid}/skus | 建立一个SKU，返回SkuVO |
| PUT | /api/product/{pid}/skus/{id} | 修改名称、规格、价格、图片或状态；stock只能核对 |
| DELETE | /api/product/{pid}/skus/{id} | 软删非默认SKU，保留原订单恢复能力 |
| GET | /api/product/{pid} | 原商品详情新增可用skus数组；上架且未删，含库存0的SKU |

创建示例：

```json
{
  "name": "黑色256GB",
  "specs": {"颜色": "黑色", "容量": "256GB"},
  "price": 20.50,
  "stock": 4,
  "image": "/assets/black-phone.png",
  "status": 1
}
```

创建要求name/specs/price/stock齐全；名称trim后最长128；价格0至99999999.99且最多两位小数；初始库存0至Integer.MAX_VALUE；图片沿用原资源地址验证；状态0/1。SKU父商品必须存在且未删，归属不允许由DTO随意更换。

specs为1–5对字符串。名称trim后1–30字符，值trim后1–50字符，禁止控制字符和trim后重复名称。服务端按名称排序后序列化JSON，用JDK SHA-256计算组合摘要，因此字段排列不同不会创建重复组合。JSON结构避免直接拼接字符串产生歧义。

同SPU组合重复返回409，包括复用仍保留该组合的软删行。默认SKU由系统用空规格`{}`创建，不能通过普通SKU创建接口伪造；默认SKU不可删除或修改规格，可以改名/改价/上下架。

更新库存不是“把库存改成某个数字”：传stock只能核对当前SKU是否仍等于该值，不一致409，SQL不覆盖stock/sales。此阶段没有增加补货接口；后续库存阶段再设计库存变更与流水。

### 3.2 新旧下单入口

新调用：

```json
{
  "items": [{"skuId": 123, "quantity": 2}, {"skuId": 124, "quantity": 1}],
  "receiverName": "测试人",
  "receiverPhone": "000",
  "receiverAddress": "测试地址"
}
```

旧调用继续接收 `{"productId":1,"quantity":2}`，只解析到productId=1的固定默认SKU。每个明细productId/skuId二选一，两个都非空或都为空返回400；重复SKU返回400。即使一项用productId、另一项用对应默认skuId，也会在解析后发现重复并拒绝。不能静默合并两项数量。

详情的OrderItemVO在原六个字段之外新增skuId、skuName、skuSpec；skuSpec是规范化JSON字符串。历史明细这些字段仍为NULL，商品名、图片和单价仍用原快照。

### 3.3 幂等摘要升级

全productId请求保持阶段02的v1字节格式，排序、收货来源、trim后的备注等语义不变，固定摘要测试继续通过。已有v1回执不改写，也不依赖当前默认SKU是否可用才能重放。

只要一单包含skuId，则使用v2：按选择器类型及ID排序，每项摘要包含`product`或`sku`标签、ID、数量，收货来源与备注规则保持不变。标签避免productId=1和skuId=1被当成同一内容。

因此同一个键从旧productId改为默认skuId仍返回409；即使最终购买对象相同，也不能重新解释已经使用的业务键。客户端应保留原键和原内容，新的一笔购买才换键。成功回执的快速返回仍在SKU解析和商品HTTP之前。

## 5. 从输入到数据库变化的真实调用链

### 5.1 商品与规格维护

```text
POST /api/product
 → 原管理门禁及DTO验证
 → ProductServiceImpl.addProduct
 → CatalogTransactions.write
 → 分类链校验/锁 → 插SPU → SkuService.createDefault → 插默认SKU
 → 同一事务提交，任一插入失败均回滚

POST /api/product/{pid}/skus
 → 管理门禁 → SkuInput / specs规范化
 → CatalogTransactions.write → 锁SPU → 插SKU
 → 组合唯一冲突在事务回滚后映射409
```

商品列表或详情在原RR快照中读SPU、参数与SKU；SkuMapper.aggregate提供最低价和汇总计数。当前按每页每个商品分别查询聚合，存在N+1查询；本阶段未声称高吞吐或性能提升，后续可在有基线后批量聚合。

### 5.2 SKU首次下单

```text
POST /api/order + Idempotency-Key
 → JWT/账号与DTO校验
 → OrderIdempotency：v1或v2摘要，先查成功回执
 → 未命中：OrderSkus解析skuId/默认SKU，按SPU去重HTTP预读
 → 原按日JVM锁与OrderTransactions.create(RC/新事务)
 → 锁用户 → 锁定检查回执 → 读收货快照
 → 解析SKU并拒绝最终重复 → 分类链锁与校验
 → 所有SPU按ID升序锁，校验分类稳定及商品可见
 → 所有SKU按ID升序锁，校验归属、可用状态、价格、计数
 → 组装商品/SKU/单价快照 → 分配单号
 → SKU stock-q/sales+q → 插订单与明细 → 插成功幂等回执
 → 整笔提交后返回
```

HTTP只作原有预读，不作为定价依据；一单同SPU多个SKU最多预读一次该SPU。真正价格和库存来自锁后的SKU。SKU管理锁SPU后锁SKU，交易也先锁完SPU再锁SKU，避免多个规格之间引入反向锁序。

### 5.3 新旧订单取消

```text
取消入口 → 锁用户 → 锁本人订单 → 检查原明细完整性
 → 所有原SPU按ID升序锁（允许已下架/软删）
 → skuId有值：恢复该SKU；skuId为空：按原productId解析默认SKU
 → 拒绝重复恢复目标 → SKU按ID升序锁
 → 校验归属与计数边界 → CAS订单置取消
 → 每个原SKU stock+q/sales-q → 同事务提交
```

取消不重算金额，不用当前SKU单价，不把已删除SKU换成其他可售规格。SKU物理缺失、归属不符或明细损坏时返回500并整笔回滚；溢出或不足409，不能只恢复其中一部分。

## 6. 默认SKU迁移、重复执行与失败恢复

### 6.1 正确执行顺序

1. 停止旧product/order及所有其他写入者，核对目标库与备份。`--maintenance`是操作者声明，不会自动停服务或封锁其他主机。
2. 使用阶段01迁移入口应用V3 DDL；不要编辑已执行V1/V2。
3. 入口自动调用sku_backfill.finish，每批最多200个商品，按主键范围逐批复制旧price/stock/sales；上架、下架、软删商品都保留默认映射。
4. 每批独立提交，只插尚无默认SKU的商品，不覆盖已有SKU。中断后从头扫描并跳过已存在映射，继续补齐；不依赖丢失的内存游标来判断完成。
5. 复制结束检查默认映射完整和旧库存/计数/价格逐行一致，才写t_catalog_migration(version=3)。历史明细和幂等回执保持原值。
6. 运行入口validate，核对Flyway历史、默认映射和完成标记，再统一启动新版product/order。

```powershell
python scripts/db_migrate.py info
python scripts/db_migrate.py migrate --maintenance
python scripts/db_migrate.py validate
```

连接变量、空库/未接管旧库的baseline分支、备份保存位置沿用sql/README.md；本文不记录真实账户密码。空库应用V1–V3后有10张业务/辅助表，另有Flyway history，不注入测试商品。已有V2库只执行V3与默认SKU回填。

### 6.2 为什么V3成功不一定表示整个切换结束

MySQL DDL可能已提交，Flyway也可能已记录V3成功，但分批数据复制尚未完成。此时不能只看history便启用业务，要检查完成标记；再次执行migrate --maintenance可以续跑。复制完成后，再次migrate不会把SPU冻结库存覆盖回已被订单修改的SKU。

如果已存在的默认SKU与旧值不一致，入口拒绝标记完成，不自动“修正”为旧值。先停写核对实际来源；若有人在维护期间启用新交易，不能用重新复制或旧备份覆盖新交易。

不支持旧新写进程混合滚动发布。旧订单二进制只认识SPU库存，重新启用它会造成双账本。代码回退不能自动撤销V3；在已有新SKU交易后恢复发布前备份会损失新增订单，须保留现场另行制定前向修复/数据恢复方案。

当前没有数据库级停写栅栏或自动启动开闸；上述步骤和完成标记检查需要操作者执行。缺默认SKU的请求会失败，不从SPU旧库存静默回退。

## 9. 失败路径如何理解

| 失败 | 行为/恢复 |
|---|---|
| SKU不存在、下架或软删，新下单 | 404，不写新订单；已成功键仍可先返回原回执 |
| 同一有效SKU出现两项或选择器混用 | 400，不能重复扣减或不明确地合并数量 |
| SKU组合已存在 | 唯一约束失败后整笔回滚，返回409 |
| SKU插入失败 | 同事务创建的SPU也回滚 |
| 某一明细库存不足或后续写入失败 | 全部SKU扣减、订单、明细、幂等回执一并回滚 |
| SKU/商品物理缺失或历史明细损坏 | 500，取消不部分恢复，不挪到兄弟SKU |
| 已提交但客户端没收到结果 | 原键查询/原内容重发，不换键盲目下第二单 |
| 回填中断 | DDL可能已完成，保持停写，原入口续跑；已有默认SKU不被覆盖 |
| 回填核对不一致 | 拒绝标记完成，保留现场；禁止用旧值覆盖已有交易 |

## 10. 设计取舍和当前限制

- 规格用规范化Map表达，一个SKU一组组合；未引入规格维度表/规格值表、自动笛卡尔积和复杂模板。组合按trim后的原始文本区分，不额外做大小写或Unicode同义归一。
- 默认SKU固定作为旧productId映射，永不改成“当前最便宜的SKU”，避免旧请求和旧订单恢复漂移。
- 商品聚合查询目前每商品一条，尚未做批量聚合优化或查询性能基线；不写性能提升比例。
- 单SKU计数为Integer边界，SPU汇总为Long；新库存只在创建时赋初值，没有资料覆盖库存的后门。
- 软删保留库存与历史恢复目标，物理删除不在接口能力内；永久历史保留与幂等回执增长仍需后续容量治理。
- 仍为共享MySQL的多个服务进程，本地库存事务是受控跨表写入；没有拆独立库存数据库，没有跨地域正确性验证。
- 本阶段要求维护窗口，未实现无停机滚动切换；迁移开关是操作声明，完成标记不是自动阻止所有进程启动的栅栏。
- 单号算法、按日JVM锁和同用户串行化仍沿用旧方案，没有因引入SKU便获得高吞吐编号能力。
- 管理SKU可通过创建返回ID及已知ID维护；暂未增加独立的含下架SKU管理列表/完整后台UI，后续后台阶段统一完善，不把公开详情当成完整管理查询。
- 本轮没有改真实业务库，也没有把已有阶段01/02的全部未提交文件计为本次原创。原有未提交内容保留。
