# 库存调整与流水接口（阶段07）

业务服务为 product，统一 context-path 为 `/api`。三个接口均要求后台 JWT 和 `inventory:adjust`；默认角色只有系统管理员、履约人员具备该权限。商品资料及 SKU 资料 PUT 继续拒绝改变库存，可省略 stock 或提交未改变的 stock。本阶段无新增生产依赖。

## 调整库存

`POST /api/product/{pid}/skus/{sid}/inventory/adjustments`

```json
{"businessNo":"IN-20261106-001","type":"INBOUND","quantity":5,"reason":"入库单001到货"}
```

- `businessNo`：1—64 位 ASCII，首位为字母或数字，其余可用字母、数字、`_ . : -`；全局唯一且区分大小写。调用方在发送前生成并保留，超时或响应丢失后重发相同请求。
- `type`：`INBOUND` 入库，quantity 必须 >0；`ADJUSTMENT` 盘点等人工调整，quantity 是有符号增量且不能为0。不是目标库存值。
- `quantity`：JSON 整数，32 位范围；计算使用 long，拒绝结果小于0或大于2147483647。
- `reason`：1—200字符，不得全空白或包含控制字符；按提交原文保存，重试时内容也必须一致。
- 同号、同 SKU、同 type/quantity/reason 重放返回原调整单，不重复修改库存或写流水/审计。不同参数/不同 SKU 复用同号返回409；跨 SKU 同号并发由全局唯一索引兜底，失败方整笔回滚。
- 返回 data：`id,businessNo,skuId,type,quantity,reason`。它是调整单，不是实时库存快照；重放后使用 balance 查询当前库存。
- 已删除商品/SKU 拒绝新调整，但已成功的原请求可在删除后重放。下架库存允许调整。

## 查询流水

`GET /api/product/{pid}/skus/{sid}/inventory/ledger?pageNum=1&pageSize=10`

可选 `type`、`businessNo` 精确过滤；type 枚举见下表。pageSize 1—100，pageNum 1—10000，按流水 ID 倒序。未知参数拒绝400。可读取软删 SKU 的历史记录；SKU 必须属于 pid。查询使用 RR 只读事务，使 total 与 records 来自同一快照。

返回 `total,records,pageNum,pageSize`；每条包含 `id,skuId,type,businessNo,quantity,salesQuantity,beforeStock,afterStock,actorId,createdAt,adjustmentId,reason`。订单事件 businessNo 即订单号；人工调整关联调整单及原因；系统或订单事件 actorId 可为空。当前 createdAt 沿用连接会话时区，部署与调用方应统一时区，不将其误称为 UTC。

## 查询账本一致性

`GET /api/product/{pid}/skus/{sid}/inventory/balance`

返回 `skuId,stock,sales,ledgerStock,ledgerSales,openingCount,consistent`。在一个 RR 快照中核对：恰有一条期初、流水 quantity 总和=当前 stock、salesQuantity 总和=当前 sales。`consistent` 为 JSON 布尔值，不能把 SQL 对账作为防篡改保证。完整验收还检查逐行 before/after 链及业务关联。

## 流水类型与账本公式

| 类型 | 业务号 | quantity | salesQuantity |
|---|---|---|---|
| OPENING | 固定 OPENING | 迁移/新建时库存（可为0） | 当时 sales |
| INBOUND | 调整业务号 | 正数 | 0 |
| ADJUSTMENT | 调整业务号 | 有符号非0增量 | 0 |
| ORDER_OCCUPY | 订单号 | -购买数量 | +购买数量 |
| CANCEL_RESTORE | 订单号 | +购买数量 | -购买数量 |
| REFUND_RESTORE | 订单号 | 预留 +购买数量 | 预留 -购买数量 |

`当前库存 = 期初 + 入库 + 人工调整 - 下单占用 + 取消恢复 + 退款恢复`。

`当前 sales = 期初 sales + 占用数量 - 恢复数量`。sales 在本项目沿用原有订单计数语义，不改成已付款销量。OPENING 不伪造迁移前订单明细；历史未取消订单后续取消时，在期初之上追加恢复。

流水唯一键 `(sku_id,event_type,business_no)` 防止同事件重写；生成列 `restore_order_no` 使取消和退款对同 SKU、同订单共用唯一恢复键。退款仅预留事件类型/约束，本阶段没有退款接口和审批实现；后续退款仍须先锁订单、验证未发货状态和恢复数量。现有取消仅允许待支付、已支付、备货中；发货后拒绝恢复。

## 事务、锁与错误

- 人工调整：后台鉴权 → 参数校验 → product 行锁 → SKU 行锁 → 读取同号调整单 → 插入调整单 → 更新 SKU → 插入流水 → 写管理审计 → 同一连接提交。
- 下单：沿用 user → category → 按 ID 排序 product → 按 ID 排序 SKU；扣减后立即追加 ORDER_OCCUPY，订单、明细、幂等回执、流水一同提交。失败全部回滚。
- 取消：沿用 user → order → 排序 product → 排序 SKU，状态 CAS 与库存恢复、流水一同提交。重复取消仍按既有契约409。
- 人工调整只获取共享锁序中的 product → SKU，不在持有 SKU 后补取上游锁。
- 400 参数错误，401 无后台身份，403 缺少权限，404 SKU不属于商品/对象缺失，409 库存不足/溢出/业务号冲突。数据库连接失败沿用503，非预期流水/审计写入失败500且回滚。缺少 OPENING 直接拒绝写入500，不在在线交易里猜测期初。
